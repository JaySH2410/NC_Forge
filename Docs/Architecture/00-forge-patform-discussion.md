**Executive Summary:** This document consolidates our Forge platform design, summarising locked-in architectural decisions and highlighting open questions.  Forge is envisaged as a metadata‑driven low‑code platform: new user features are built via configuration and data (metadata and admin data), not custom code.  We define three personas (Core Developer, Platform Admin/Configurator, End User) and three logical layers (Metadata, AdminConfigData, BusinessData), with distinct storage containers (MetaSchemas, AdminConfigs, BusinessData).  The versioning scheme follows Semantic Versioning (Major.Minor.Patch plus an object‐revision counter), and each object has lifecycle states (Draft/Published/Archived).  Deployment will use OCI‑style package files (a “.bakpak” archive) and an audit log; import is transactional with a “deactivate-old + insert-new” strategy for updates, ensuring atomicity.  Access control is RBAC: roles have row+action policies (View/Create/Edit/Delete) with Allow/Deny and Deny-overrides rules.  The policy model v1 is locked, and areas like deployment unit scope, re-import semantics, MasterPrefix handling, data migration, etc., are marked OPEN with concise options.  A comparison table and an import‐pipeline flowchart are included.  Prioritised references for implementation include PostgreSQL’s transaction docs, the OCI Image v1.1 spec, OWASP integrity guidelines, RFC2119/SemVer, and examples of metadata-driven platforms (Salesforce, OData). 

1. **Vision & Personas.**  Forge is a *metadata-driven* platform for building business apps.  Metadata defines structure (objects, fields, UI, logic) so the platform auto‑generates much of the UI and CRUD functionality.  *Core Developers* build the Forge engine and primitives; *Platform Admins/Configurators* define metadata, interfaces, properties, views and package them; *End Users* work with the configured apps and runtime data.  The core goal is that new end-user features come from moving configuration & data, not writing new backend code.

2. **Layered Architecture.**  Forge has three conceptual layers: **Metadata** (the schema definitions: Classes, Interfaces, Properties, Relationships, Views, Graphs, etc.), **AdminConfigData** (application configuration – e.g. Class<>Interface<>Property assignments, view layouts, interface hierarchies), and **BusinessData** (the runtime records of those business objects).  Each layer is stored in its own container: e.g. a global *MetaSchemas* DB schema/table, a global *AdminConfigs* store, and a multi-tenant *BusinessData* store.  BusinessData is further scoped by BusinessEntity, BU, Department, Site, etc.  This separation ensures that tweaking metadata/config rarely requires code changes, and different tenants can share or isolate business data.

3. **Scope & Placement Model.**  We assign objects to containers/scopes as follows: Metadata (Classes, Interfaces, etc.) is global across the platform (container `MetaSchemas`); AdminConfigData (application-specific schema usage) is also global or per-tenant (container `AdminConfigs`); BusinessData is tenant-bound and further partitioned (table `BusinessData` keyed by BusinessEntity, BU, Dept, Project, etc.).  In simple terms, Metadata/AdminConfigData goes into fixed global schemas, while BusinessData is sharded by organizational hierarchy.  This ensures e.g. all users see the same class/interface definitions, while their data is isolated.  (Open: Define exact container naming conventions and multi-tenancy isolation strategy.)

4. **Modeling Principles.**  We enforce a strict schema model to simplify engine logic: **Interfaces** carry all properties and relationship definitions; **Classes** attach to interfaces but do not hold properties directly.  Every Class must implement one primary interface plus an internal IObject interface.  Classes may implement additional interfaces, but interfaces do *not* inherit from each other in v1 (no interface inheritance).  Relationships (one-to-many) are defined at the interface level (so all implementers share them).  Graphs and Views reference interfaces/classes by ID.  (OPEN: reconsider interface inheritance or complex types in future versions.)

5. **Metadata & AdminConfig Concepts.**  Key metadata objects: *Object (Class)*: schema entity (e.g. Employee); *Interface*: a named set of properties (e.g. IPerson includes Name, Email); *Property*: name+type (primitive, enum, or interface-ref); *Relationship*: 1:N links between interfaces; *Type*: enum or primitive schema.  An *Application* is a collection of AdminConfigData (specific Classes, Interfaces, Views, etc.).  Every Class/Object has a version and state (Draft/Published/Archived).  (No external citations – definitions are domain-specific.)

6. **Versioning & Lifecycle.**  Forge adopts **Semantic Versioning** for application artifacts.  We represent versions as `app_major.app_minor.app_patch` (e.g. 2.3.1 for the app release) and combine that with an object-specific revision (e.g. `.r5`) to get a full `2.3.1.r5` label.  *Lifecycle states* per object are **Draft** (editable), **Published** (active), and **Archived** (inactive legacy).  Once an object is Published, its schema is effectively frozen (new changes go to a new version).  Merging or importing configurations must respect these versions.  (OPEN: define how App vs Object versions reset, and whether to support build metadata or prerelease tags.)

7. **Package & Deployment Strategy.**  We will deploy configurations using a Forge package file (akin to an OCI Artifact or “.bakpak”).  This package is a non-human-readable archive (e.g. compressed/JSON) that contains metadata and AdminConfigData.  Each package includes a manifest listing its contents and versions.  On upload to Forge, an import task is created and logged.  This follows OCI’s Artifact guidance: e.g. using an `artifactType` or custom mediaType in the manifest to distinguish it, and using the subject/referrers model if needed.  (RECOMMENDATION: treat each package as an **OCI artifact** to leverage registries and signatures.)  The package can be for a whole App (all its objects/views) or subsets.

8. **Import Workflow (pipeline).**  Import proceeds in stages:  
   - *Validation*: The uploaded package is first checked for schema validity, dependency consistency (e.g. if Class X implements Interface Y, both must exist), and semantic version compatibility.  
   - *Dry-Run*: If valid, a dry-run applies changes in a temporary transaction (no DB commit) to detect runtime errors (e.g. unique key violation, conflicting changes).  
   - *Import*: If dry-run passes, Forge executes the import (within a single DB transaction) committing changes.  
   - *Activate*: Newly imported objects in state “Published” are now live; older versions are deactivated.  

 *Figure: Conceptual data import pipeline (validate → dry-run → import → activate).*

   This pipeline ensures atomicity and gives admin feedback.  All steps and results are recorded in an *import history log* for audit.  (OPEN: flesh out UI/UX for conflict resolution – e.g. how administrators review dry-run errors or merge choices.)

9. **Transactional Import Guarantees.**  All import steps must be **atomic**: on any error, the database rolls back completely.  PostgreSQL transaction semantics give us ACID guarantees (atomicity, consistency, isolation, durability): either the entire package import succeeds (making all changes durable), or no change is applied.  We should use a single transaction per import (with savepoints if needed) so *no partial state* is visible.  This means e.g. creating new Classes and then failing later will undo all class creation.  Also ensures no crash can leave half-applied config.  (RECOMMENDATION: wrap import in BEGIN…COMMIT with ROLLBACK on failure.)

10. **Package Content Options.**  We must decide what layers a package may include.  Options include:  
   - *Metadata only:* includes only schema (Classes, Interfaces, Properties). Useful for schema sync, but AdminConfigData must be applied separately.  
   - *AdminConfig only:* contains only application usage of existing schema (instantiating Classes, setting up views, etc.), assuming metadata already exists.  
   - *Combined (Metadata + AdminConfig):* self-contained app package including both schema and configuration.  
   - *Full (including sample data):* add sample BusinessData for seeding. (Likely postponed.)  

   | **Option**        | **Layers Included**         | **Use Case**                    | **Pros**                          | **Cons**                      |
   |-------------------|-----------------------------|---------------------------------|-----------------------------------|-------------------------------|
   | Metadata-only     | Classes, Interfaces, Props  | Propagate schema definitions    | Lightweight; reusable in many apps | May need matching AdminConfig |
   | AdminConfig-only  | App-specific config (class–interface links, views) | App customization changes         | Small changesets for live updates  | Fails if metadata differs    |
   | Combined Package  | Metadata + AdminConfigData  | Onboarding new apps/tenants      | Self-contained, versioned config   | Larger package; more merge logic |
   | Full + Data (TBD) | Above + BusinessData samples | Initial tenant setup (seed data) | End-to-end deployment including sample records | Risk of overwriting user data |

   (OPEN: finalize package type policy – allow all types vs enforce “full app” style.  Also define format: JSON+zip? OCI registry image?)

11. **Idempotency & Re-import.**  Re-import semantics are subtle.  If the *same* package (same version+contents) is applied twice: do we *ignore* (no-op), *error*, or *log as duplicate*?  We recommend idempotent imports: detect identical versions and treat as no-op (but record in log).  If a package with already-imported object definitions but newer object revision arrives (e.g. App version bumped, object schema changed), apply using the *deactivate-old+insert-new* pattern.  This is like Git’s append-only tag rule.  If the incoming version is identical but objects have changed (e.g. name conflict, same label but different UID), we should reject to avoid ambiguity.  (OPEN: define clear rules – e.g. fail on name collision, require a flag to force overwrite.)

12. **Name/UID Conflicts & MasterPrefix.**  We must handle identifier collisions.  - **MasterPrefix collision:** every object carries a MasterPrefix (like namespace).  If an imported package’s prefix clashes with existing prefix in target (same prefix but different ownership), the import should either fail or require renaming.  Recommendation: treat prefix collision as error to maintain global uniqueness.  - **Same UID, different content:** if an object’s UID matches an existing one but its schema changed incompatible, deactivate old and insert new (as above).  - **Same name, different UID:** treat as distinct; allow separate objects if unique IDs differ, but warn on confusion.  - **Partial failure:** if some objects in package conflict, roll back entire import (atomic).  (OPEN: decide on overwrite vs skip policy per-object; UI to resolve conflicts.)

13. **Dependency & Promotion.**  Packages may have inter-dependencies (one interface may depend on another).  Import must validate that all referenced objects are present in the package or already exist; if not, either error or auto-import missing pieces.  We should apply a topological import order (similar to CI/CD dependency graphs).  Also plan promotion across environments: we likely treat a package as the unit of promotion (e.g. between Dev→QA→Prod), rather than ad hoc object exports.  (OPEN: finalize promotion model – e.g. use a registry or VCS-based deployment; handle simultaneous object changes across multiple apps.)

14. **AdminConfig Reuse & App Composition.**  Shared objects (e.g. an Employee object) might appear in multiple apps (HR, Assets, etc.).  We want one canonical definition to avoid duplication.  *Owning app* concept: the first app to create the object “owns” it.  Other apps may *consume* it via relationship.  For app-specific extensions, we plan *extension objects*: e.g. HRApp can define an EmployeeExtended that is separate from core Employee.  This avoids modifying the shared object.  (OPEN: define explicit “extension-of” relations vs plain inherit; policy for versioning shared objects when an owning app upgrades and others use it.)

15. **RBAC & Scope Model.**  Forge has the common elements: *Role*, *Permission*, *UserRole*, *UserContainerScope*, *PolicyAttachment*.  Roles group permissions; permissions link roles to actions on objects; policies attach on Roles (or Users) with conditions.  Data can be scoped by container (e.g. BU or Dept) and policies filter accordingly.  Users are associated with a business unit and roles.  Policies enforce access at runtime.  (Open: we’ll unify metadata vs data permissions eventually – e.g. who can edit a Class vs who can create data – but initial focus is on data.)

16. **Policy Model (v1 Locked).**  In v1, policies apply only to **BusinessData** and attach to **Roles** (not directly to Users).  Each policy record is for a Role+BusinessObject+Action.  Supported *actions* are View/Create/Edit/Delete.  Policies are **row-level** (filter which records) plus action-level; *field-level restrictions* are not in v1.  Policy *effects* can be **Allow** or **Deny**.  When a user requests an action: all matching policies are evaluated – any Deny wins, else any Allow, else default Deny.  Conditions in policies may compare user context vs record fields.  Allowed fields: user context (UserId, BusinessEntity, BU, Dept, Site, SubSite, Project) and record context (CreatedBy, BusinessEntity, BU, Dept, Site, SubSite, Project, Status).  Supported operators: `=` `!=` `IN` `NOT IN` `IS NULL` `IS NOT NULL`.  Conditions combine only with AND (no OR).  *Example:* Role=Editor might have “Allow Edit on Invoice if record.Department = currentUser.Department”.  (Implementation will log policy evaluation for audit.) 

17. **Policy Extensions (OPEN).**  In future versions we may extend policies to cover Metadata/AdminConfig actions (e.g. who can publish a new interface), field-level restrictions, or even time-based conditions.  Should policies attach per-object or per-role only?  Recommendation: keep Role-bound but reference the target object in policy records (as in v1).  Also consider *deny-by-default* for new object types.  (OPEN: field-level policies? label-level policies? policy UI?).

18. **OPEN ITEMS & Decisions.**  The following remain to decide (concise options given):

- **Deployment unit name/types (OPEN):** e.g. “Application package” vs “Feature bundle” vs “Tenant config”. *Option:* Use **Application** as unit (natural grouping of objects); *Option:* allow smaller **Feature** bundles (more flexible); *Option:* full **Tenant** backup (monolithic).  
- **Package contents (OPEN):** as above table. Decision pending: probably allow both metadata-only and combined packages.  
- **Import re-run behavior (OPEN):** *Option:* silently skip duplicates (idempotent); *Option:* error on re-import; *Option:* log as “skipped duplicates.”  
- **MasterPrefix handling (OPEN):** *Option:* enforce global uniqueness (fail on clash); *Option:* allow remapping prefixes on import (complex).  
- **Import failure strategy (OPEN):** *Option:* complete rollback on any error (safe, simpler); *Option:* partial import (commit non-conflicting parts, skip failures – complex).  We recommend full rollback.  
- **Dependency resolution (OPEN):** *Option:* require explicit pre-ordering (admin manually orders imports); *Option:* automatically topologically sort package entries (tool-assisted).  
- **Version merging (OPEN):** Rules for “same name/different UID”: usually error out, or require re-tagging. *Option:* reject colliding names by default.  
- **Promotion between environments (OPEN):** *Option:* use packages (import/export) for Dev→QA→Prod; *Option:* use Git-like diff exports; *Option:* something like Blue/Green deploy per object.  
- **Policy on metadata (OPEN):** Extend v1 to cover AdminConfigData/Metadata publishing. *Option:* defer to a later version.  
- **AdminConfig reuse (OPEN):** Finalize owner vs consumer model and extension object pattern.  
- **Import security (OPEN):** *Signing:* use code-signing or OCI signatures (sigstore) on packages; *Encryption:* possibly encrypt sensitive data or support server-side encryption. OWASP recommends protecting signing keys (e.g. HSM) and verifying signatures.  
- **UI/Conflict resolution (OPEN):** How to present merge conflicts or require human approval (similar to code review vs auto-apply).
